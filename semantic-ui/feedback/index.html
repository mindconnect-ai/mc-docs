Loading & progress

semantic-ui has two distinct ways to tell the user "something is happening", and the difference matters:

  • Declarative — a UiSpinner or UiProgress node you place in the tree and later swap out with a patch when the data arrives. Use it as a placeholder (an empty card, a not-yet-loaded panel) or to show a running task's progress.
  • Automatic — when a control fires a trigger, the event bus marks that control busy for the duration of the request (an is-loading class the CSS turns into a small spinner, plus aria-busy). You write no node for this; it just works on every button, link and form submit.

Both render identically in the SSR (Handlebars) and SPA (TypeScript) paths.

Spinner​

A busy indicator: a spinning glyph, optionally with a label. Sizes are SM, MD (default) and LG.

UiSpinner.of();                                  // bare, decorative
UiSpinner.of("Loading…");                        // with a visible label
UiSpinner.of().size(UiSpinner.Size.LG);          // large
{ "type": "spinner", "id": "busy", "size": "LG", "label": "Loading…" }

The glyph inherits the surrounding text colour (currentColor) and scales with the font. A title (or the visible label) becomes the accessible name (role="status"); without one the spinner is decorative (aria-hidden).

Progress​

A BAR (default) or CIRCLE indicator. Set value against max (default 100) for determinate progress; omit value for an indeterminate loop. status tints the fill (SUCCESS / WARNING / ERROR), and showValue toggles the NN% readout.

UiProgress.of(60);                                          // a 60% bar
UiProgress.of(30, 120);                                     // 30 of 120 → 25%
UiProgress.of(100).status(UiProgress.Status.SUCCESS);      // green, done
UiProgress.of(45).variant(UiProgress.Variant.CIRCLE);      // a ring
UiProgress.indeterminate();                                 // unknown duration
{ "type": "progress", "id": "upload", "value": 60, "status": "NORMAL" }

Driving progress from the server​

Push updates the same way you update any node — a REPLACE patch on the progress node's id:

{ "patches": [
  { "op": "REPLACE", "targetId": "upload",
    "node": { "type": "progress", "id": "upload", "value": 80 } }
] }

Automatic inline loading​

Any control that dispatches a trigger (a UiAction button, an action rendered as a link, a form submit) is decorated with an is-loading class while its request is in flight. The CSS paints a small spinner on it and blocks a second click; the class is removed when the request settles. Nothing to configure:

// Clicking this shows a spinner on the button until the POST resolves.
UiAction.primary("save", "Save").icon("save")
        .onClick(UiTrigger.api("POST", "/products"));

The feedback is tied to the same policy as the global loading indicator. To turn it off for a page (e.g. a chat surface that manages its own affordances):

bus.setLoadingPolicy("manual");   // suppresses both the global bar and inline spinners

"auto" (the default) shows it on every dispatch; a predicate (ctx) => boolean decides per-trigger.

A link can dispatch a trigger too — give UiLink an onClick and it fires a fetch/patch (and gets inline loading) instead of navigating; href stays as the no-JS fallback:

UiLink.of("more", "/items?page=2", "Load more")
      .onClick(UiTrigger.api("GET", "/items?page=2"));

Setting the loading state yourself​

The automatic behaviour covers "this control's own click is in flight". When the server owns the state instead — you want a button to stay busy across a re-render, or to show busy without a click — set it on the model with loading:

UiAction.primary("save", "Saving…").loading(true);   // rendered busy + disabled
{ "type": "action", "id": "save", "label": "Saving…", "style": "PRIMARY", "loading": true }

Typical flow: the click handler returns a patch that replaces the button with loading:true, and a later patch replaces it again with the finished button.

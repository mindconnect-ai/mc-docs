Navigation menu

UiMenu is a collapsible vertical navigation sidebar — the kind an admin shell puts on the left. It holds nestable UiMenuItems and toggles between three states with a hamburger:

  • expanded — icon + label; groups expand inline (accordion)
  • rail — a narrow icon-only strip; groups appear as hover fly-outs, leaves show a tooltip
  • hidden — off-canvas; only the hamburger remains
UiMenu.of("nav", "Admin",
    UiMenuItem.link("dash", "Dashboard", "/dash").icon("dashboard").selected(true),
    UiMenuItem.group("catalog", "Catalog",
        UiMenuItem.link("prod", "Products",  "/products").icon("tag"),
        UiMenuItem.link("cust", "Customers", "/customers").icon("users")
    ).icon("grid").open(true),
    UiMenuItem.of("reload", "Reload").icon("refresh")
        .onClick(UiTrigger.api("POST", "/reload")),        // dispatches instead of navigating
    UiMenuItem.link("logout", "Log out", "/logout").icon("logout")
).state(UiMenu.State.EXPANDED);
{ "type": "menu", "id": "nav", "title": "Admin", "state": "EXPANDED",
  "items": [
    { "type": "menu-item", "id": "dash", "label": "Dashboard", "icon": "dashboard", "href": "/dash", "selected": true },
    { "type": "menu-item", "id": "catalog", "label": "Catalog", "icon": "grid", "open": true, "children": [
      { "type": "menu-item", "id": "prod", "label": "Products", "icon": "tag", "href": "/products" }
    ] }
  ] }

Items: leaves, groups, triggers​

Each UiMenuItem is a full UiNode (type: "menu-item"), so a patch can REPLACE a single entry — flip selected, swap a label, add a count — without re-rendering the whole menu.

  • A leaf with href navigates. Give it an onClick trigger instead and it dispatches through the event bus (fetch/patch) with inline loading, keeping href as the no-JS fallback.
  • A group (an item with children) nests further items to any depth. open controls its initial expanded state.
  • icon is what shows in the rail — give every top-level item one.
  • selected marks the active item (aria-current="page").

The three states​

state is the initial state the server renders. What happens next depends on the environment:

  • With the SPA event bus the hamburger cycles expanded → rail → hidden → expanded entirely client-side (no server round-trip) and remembers the choice in localStorage. Call restoreMenuState(root) once after renderer.mount(...) so that choice survives reloads:

    import { restoreMenuState } from "@mc/semantic-ui/renderer.js";
    renderer.mount(page);
    restoreMenuState(root);

  • Server-driven is free: render (or patch) the menu with any state and it appears that way. Useful if you'd rather keep the collapse state on the server.

  • With no JS at all the menu still works: items are real <a href> links, groups are native <details> disclosures (expand/collapse without script), rail fly-outs are pure CSS :hover, and a checkbox-hack hamburger shows/hides the list.

Push vs. overlay​

mode decides how the sidebar relates to the content beside it:

  • PUSH (default) — the menu takes up layout space. Place it next to the content in a horizontal UiStack; as the menu collapses to a rail or hides, the content reflows wider.
  • OVERLAY — the menu is a drawer that floats over the content with a dimmed backdrop; the content doesn't move. HIDDEN slides it off-canvas. Overlay needs its container to be a positioning context (CSS position: relative), and pairs naturally with a header hamburger.
  • RESPONSIVE — the usual admin-shell behaviour: push on a wide screen (the hamburger flips expanded ⇄ rail, so the sidebar never fully vanishes) and an overlay drawer on a narrow one (closed by default; the hamburger opens it, the backdrop closes it). The breakpoint is max-width: 768px.
UiMenu.of("nav", "Acme", items).mode(UiMenu.Mode.RESPONSIVE);
tip

When the hamburger lives in the header (.toggle(false) on the menu), a PUSH menu in the HIDDEN state collapses away completely rather than leaving an empty rail. A menu that keeps its own toggle instead leaves a slim strip so it can be reopened.

Combining with a header (an app shell)​

The hamburger doesn't have to live in the sidebar. Set UiHeader.menuToggle to a menu's id and the header renders the burger in the top bar (turn the menu's own toggle off with .toggle(false)). The whole shell is just composition — header on top, [menu, content] in a horizontal stack:

var menuId = "nav";
UiStack.of(
    UiHeader.of("Acme Admin").menuToggle(menuId)          // hamburger in the top bar
        .user(UiHeader.User.of("Ada", "AL", "/me")),
    UiStack.of(
        UiMenu.of(menuId, "Acme", items)
            .mode(UiMenu.Mode.PUSH).toggle(false),         // header owns the burger
        contentPanel                                       // your page body
    ).direction(UiStack.Direction.HORIZONTAL)
        .withCssClass("app-body")                          // position: relative for OVERLAY
).direction(UiStack.Direction.VERTICAL);
.app-body { position: relative; overflow: hidden; align-items: stretch; }

Switch that one menu to Mode.OVERLAY and the same shell becomes a drawer layout — no other change.

Left or right​

side places the menu on either edge (LEFT default). It mirrors the visual orientation — the border edge, the direction rail fly-outs and tooltips open, and the way an overlay drawer slides out. For a PUSH menu, also order it on the matching side of the content in the stack (menu before the content for left, after it for right):

UiMenu.of("nav", "Acme", items).side(UiMenu.Side.RIGHT);

Badges​

An item can carry a short badge (a count or status). It sits after the label and shrinks to a dot on the icon in the rail:

UiMenuItem.link("orders", "Orders", "/orders").icon("table").badge("12");

Styling​

Widths are CSS variables on .sui-menu — override per app:

.sui-menu { --sui-menu-w: 260px; --sui-menu-rail-w: 56px; }
